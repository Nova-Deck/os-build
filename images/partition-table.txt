# novadeck A/B image partition table.
#
# SteamOS-style atomic-update layout (cf. the steamos-teardown reference):
# a shared ESP, A/B boot partitions, A/B read-only Btrfs roots, A/B /var, and a shared
# /home. RAUC writes the inactive rootfs/var slot, then the bootloader switches on success.
#
# efi-a/efi-b are each a slot's STAGE 2 home (Phase 5; docs/phase5.md): steamcl.efi on the
# shared ESP chainloads \EFI\steamos\grubaa64.efi on the slot's efi partition, whose per-slot
# grub.cfg boots the kernel in the slot root's /boot. Each carries the stage-2 GRUB + its
# identity partsets (/SteamOS/partsets/{A,B,all,shared,self,other}); steamcl matches the efi
# uuid of the partition it was loaded from against partsets/self. 64M each is ~2x
# the current stage-2 tree.
#
# All 8 partitions mirror the SteamOS layout exactly (esp, efi-A/B, rootfs-A/B, var-A/B, home).
#
#   p8 home  — the deck user's home. Two build-time choices, neither a layout divergence:
#              it is PRE-SEEDED with the native arm64 Steam client (images/make-sdcard.sh) so a
#              first boot needs no network — Steam's own OOBE owns first-boot Wi-Fi, and the
#              pre-seeded /home is the only client copy. There is no in-place re-seed: a factory
#              reset is a reflash of the card, and an internal UFS install is recovered by booting
#              a separate SD-card image. And home must stay LAST on disk: novadeck-grow-home
#              expands it to fill the card on first boot, so nothing may follow it.
#
# efi-a/efi-b are typed 0700 (Microsoft basic data), NOT ef00 — exactly as SteamOS types
# them. Only p1 is an EFI System partition. The ROCKNIX ABL finds the ESP by type GUID, so
# a second ef00 on the disk would give it two candidates to choose between. The stage-2
# grubaa64.efi is reached by steamcl, not by UEFI firmware scan, so it does not need ef00.
#
# The ESP carries GPT bit 63 ("no-auto") for the same reason home does: that GUID would make
# systemd's gpt-auto generator auto-mount it at /efi, and /efi is the name the initramfs
# reserves for the SLOT's efi-a/b partition (mounted from steamos.efi=PARTUUID=, phase 5).
# The ESP's one and only mount definition is the /esp entry images/assemble-rootfs.sh puts in
# /etc/fstab — bit 63 disables the competing generator without touching the type GUID the
# firmware scans by.
#
# Root slots are 7G. They carry, on top of the ~1.8G OS, three large x86-emulation artifacts
# that must travel WITH the slot to keep an A/B update atomic and rollback-safe: the FEX x86
# guest rootfs (~1.9G, an erofs image) and TWO bundled arm64 Proton compat tools (~2.0G each —
# the user picks per title). That is ~7.6G of content uncompressed, but the root is sealed
# read-only and baked with zstd (assemble-rootfs.sh). The emulation payloads are already packed
# and compress little (the .ero gives back barely 30%), so most of the result is incompressible
# and won't shrink in future builds. The OS half is now the SMALL half: at zstd:3 the three
# payloads are ~2.9G of the image and everything else is ~0.8G.
#
# Size against the image's APPARENT size, not its content. mkfs.btrfs --shrink cannot pack
# below its block-group granularity, so the image reports ~2G more than it actually occupies
# (5.7G apparent vs 3.7G on disk, measured 2026-07-27) — and the apparent size is what has to
# fit the partition. These slots were 6G, sized off the ~5.0G compressed content with a
# nominal ~1G of headroom; that accounting was against the wrong number, and the slot
# overflowed by 21MiB once scx-scheds and a newer Proton landed. 7G restores real headroom.
#
# The 2026-07-27 trim (images/trim.list + the mesa/scx-scheds dependency surgery) took 914MiB
# off the staged tree and 392MiB off the apparent image. The slots stay at 7G: the headroom is
# the point, and 4b needs room for a bundle to land next to a running system.
# Both are deliberately kept INSIDE the root slot rather than on a shared partition: they are
# versioned OS components, and sharing them across slots would let an update mutate the running
# system's emulation stack and break rollback.
#
# 'rest' expands to fill the target device. Fixed partitions total ~15.2G (the ESP grew by 256M,
# see above), so the minimum usable card is 32G (leaving ~15G of /home); 64G+ is the sane target.
#
# 'attrs' is a comma-separated list of GPT attribute bits to set, or '-' for none. Only bit 63
# ("no-auto") is used today, on home and on the ESP — each for its own reason, both above.
# home carries the discoverable "Linux /home" type GUID
# (8302) because systemd-repart matches it by that GUID to grow it on first boot — matching by
# type is what guarantees repart can never touch a root partition. But that same GUID also makes
# systemd's gpt-auto generator synthesize its OWN home.mount, which would silently shadow (or be
# shadowed by) the one /etc/fstab already declares, with different options and no growfs. Bit 63
# tells gpt-auto to skip the partition while leaving the type GUID — and so repart — intact.
#
# Consumed by images/genpart.sh to emit an sgdisk script. Row order = partition number.
#
# THE ESP IS 512M FOR A REASON THAT IS NOT CAPACITY, AND SHRINKING IT IS A REGRESSION.
# It holds four small files (~200K). It is 512M because a FAT32 filesystem must have at least
# 65525 data clusters to be one, and cluster count is driven by SECTORS, not bytes:
#
#   256M on 512-byte sectors   524288 sectors ->  516190 clusters   valid
#   256M on 4096-byte sectors   65520 sectors ->   65360 clusters   INVALID, by 165
#
# Every SD card is 512e and every internal UFS in this fleet is 4Kn, so a 256M ESP is a valid
# FAT32 on every card ever flashed and an invalid one on every internal install. `mkfs.vfat` was
# already at `-s 1`, the smallest cluster available, so there was no filesystem-side fix: the
# partition has to be big enough. 512M gives ~131000 clusters at 4K, with margin.
#
# MEASURED, on an AYANEO Pocket ACE, 2026-08-21. The first internal install produced an ESP Linux
# mounted happily and the ROCKNIX ABL refused, reporting no /EFI/BOOT/bootaa64.efi when the file
# was demonstrably there. Reformatting that same partition as a spec-valid FAT16 did not help
# either, so FAT32 is what the firmware wants and the size is the only lever. The peer distro's
# own internal installer makes its boot partition 2 GiB, which is why it never met this.
#
# CONSEQUENCE FOR DEVICES ALREADY IN THE FIELD, recorded because it is permanent: this file ships
# INSIDE the rootfs, so after the next OTA a flashed card runs a rootfs whose table says 512M while
# its disk still has 256M. Nothing breaks -- every runtime consumer (initramfs/init, lib-slotwrite,
# gen-grub-cfg) reads names and ORDER only, never a size, and OTA never repartitions. But the two
# do diverge, permanently, and guard-rootfs.sh cannot see it because both copies agree with each
# other. If anything ever starts validating geometry against this table, that is the case to handle.
#
# name      size  typecode  fs        label            attrs
esp         512M  ef00      vfat      NOVADECK-ESP     63
efi-a       64M   0700      vfat      novadeck-efi-A   -
efi-b       64M   0700      vfat      novadeck-efi-B   -
rootfs-a    7G    8300      btrfs     novadeck-root-A  -
rootfs-b    7G    8300      btrfs     novadeck-root-B  -
var-a       256M  8300      ext4      novadeck-var-A   -
var-b       256M  8300      ext4      novadeck-var-B   -
home        rest  8302      ext4      novadeck-home    63
